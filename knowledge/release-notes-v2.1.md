# Блокирующие вопросы

## Б1. Куда уходят расшифровки

В шапке приложения указан провайдер DeepSeek. Важно, как именно он подключён:

| Вариант | Куда уходят данные | Что делать |
|---|---|---|
| Облачный API DeepSeek (api.deepseek.com или посредник) | Тексты выступлений сотрудников банка уходят на серверы за рубежом | До использования с реальными выступлениями — согласовать со службой информационной безопасности. Скорее всего, потребуется вариант ниже |
| Открытая модель DeepSeek на своём сервере (Ollama, vLLM, llama.cpp) | Никуда за пределы сервера | Подходит. Убедиться, что сервер в доверенном контуре |
| GigaChat 3.1 Lightning на своём сервере | Никуда за пределы сервера | Рекомендуемая альтернатива: открытая модель Сбера, MIT-лицензия, официальная сборка GGUF, работает на обычном сервере |

Приложение подключается к любой модели через «Настройки» → «OpenAI-совместимый шлюз»: адрес вида `http://<сервер>:11434/v1` и имя модели.

Ещё два момента:
- **Ключ API.** Если ключ облачного провайдера вводится в настройках браузера, он хранится у каждого пользователя в открытом виде. Лучше держать ключ на сервере, за небольшим прокси, и выдавать пользователям только адрес прокси.
- **Логи.** На прокси или шлюзе отключите запись тел запросов: в них целиком лежат расшифровки.

## Б2. Доступ к серверу

Сейчас приложение открывается по голому IP-адресу. Нужно:
- **Доменное имя и нормальный TLS-сертификат.** Без доверенного сертификата браузеры показывают предупреждение, а на некоторых устройствах не дают доступ к микрофону и не включают офлайн-режим.
- **Вход по логину.** Минимум — HTTP Basic Auth в nginx или доступ только из VPN / по белому списку адресов. Лучше — корпоративный вход (SSO).
- **Где хранятся данные.** В исходной версии записи, расшифровки и разборы лежат только в браузере пользователя (IndexedDB), сервер отдаёт лишь файлы приложения. Если вы добавили хранение на сервере — нужны резервное копирование, срок хранения и разграничение доступа.

## Б3. Персональные данные

В отчёте со скриншота видны имя с отчеством и номер кабинета. Исправления — в разделе П7: правило в промптах и маскирование очевидных данных до отправки в модель. Маскирование ловит не всё: имена без отчества, названия компаний. Поэтому главная защита — Б1 (модель в своём контуре) плюс инструктаж: не называть клиентов, суммы и условия договоров во время записи.

# Ошибки логики

## П1. График темпа показывает пики и нули

**Что видно.** На графике «Слов в минуту» минуты с 0 слов чередуются с пиками около 200. Так не говорит никто.

**Причина.** Все слова строки расшифровки записывались в минуту её таймкода. Если строки идут реже раза в минуту (расшифровка по репликам, длинные абзацы), часть минут остаётся пустой, а в другие попадает текст за 2–3 минуты. Дополнительно реплики слушателей («Клиент: …») считались речью выступающего.

**Исправление** (`app.js`). Новая функция `paceByMinute` распределяет слова строки равномерно до таймкода следующей строки:

```js
/* Темп по минутам. Слова каждой строки распределяются равномерно на отрезок
   от её таймкода до таймкода следующей строки (или до конца записи).
   Реплики слушателей занимают время, но в темп выступающего не входят. */
function paceByMinute(lines, duration){
  const mins = Math.max(1, Math.ceil(duration/60));
  const arr = new Array(mins).fill(0);
  const timed = lines.filter(l=>l.t!=null).sort((a,b)=>a.t-b.t);
  timed.forEach((ln, k)=>{
    const w = LISTENER_RE.test(ln.text) ? 0 : tokens(ln.text).length;
    if(!w) return;
    const start = Math.min(ln.t, duration);
    let end = k+1 < timed.length ? timed[k+1].t : duration;
    if(!(end > start)) end = Math.min(duration, start + w/2.2) || start + 1;
    const span = end - start;
    let t = start;
    while(t < end - 1e-6){
      const i = Math.min(mins-1, Math.floor(t/60));
      const next = Math.min(end, (Math.floor(t/60)+1)*60);
      arr[i] += w*(next-t)/span;
      t = next;
    }
  });
  const tail = duration - (mins-1)*60;           // последняя неполная минута
  if(tail>15 && tail<60) arr[mins-1] = arr[mins-1]*60/tail;
  else if(tail<=15 && mins>1) arr.pop();
  return arr.map(v=>Math.round(v));
}
```

В `computeMetrics` реплики слушателей исключаются из подсчёта слов, а темп считается новой функцией:

```js
const LISTENER_RE = /^\s*(клиент|слушатель|вопрос из зала|участник)\s*[:：]/i;
function computeMetrics(parsed){
  // считаем только речь выступающего: реплики «Клиент: …» исключаем
  const own = parsed.lines.filter(l=>!LISTENER_RE.test(l.text));
  const text = own.map(l=>l.text).join('\n');
  // …дальше без изменений, кроме блока темпа:
  if(parsed.timed && parsed.duration){
    m.paceSeries = paceByMinute(parsed.lines, parsed.duration);
  }
```

**Как проверить.** Строки каждые 2 минуты по 260 слов → график ровный, 130 слов в минуту каждую минуту, без нулей. Реплика «Клиент: …» на 100 слов не увеличивает число слов выступающего.

## П2. Вердикт не совпадает с правилами

**Что видно.** 45/100 и «Нужна доработка». По правилам базы знаний ниже 50 баллов — «Нужна повторная подготовка».

**Причина.** Вердикт выбирала модель на последнем шаге.

**Исправление** (`app.js`). Вердикт считается кодом:

```js
/* Вердикт считается кодом по правилам базы знаний, а не выбирается моделью. */
function computeVerdict(total, claims){
  if(total==null) return '';
  const list = Array.isArray(claims)?claims:[];
  const err = list.filter(c=>c.status==='ошибка').length;
  const prom = list.filter(c=>c.status==='недопустимое обещание').length;
  if(total<50 || (prom>=1 && err>=2)) return 'Нужна повторная подготовка';
  if(total>=80 && err===0 && prom===0) return 'Готов к клиенту';
  return 'Нужна доработка';
}
```

`computeScores` возвращает вердикт вместе с баллами:

```js
  return {rows, total, verdict: computeVerdict(total, findings.facts?.claims), kbGap: acc.kbGap, notInKb: acc.notInKb};
```

В `finishReport` вердикт модели сохраняется для истории, а показывается рассчитанный:

```js
function finishReport(mode, ctx, metrics, findings, final, conf, iter, log, extra){
  const scores = computeScores(findings, metrics);
  final = {...(final||{})}; final.verdict_llm = final.verdict_label; final.verdict_label = scores.verdict;  // вердикт — только из кода
  const r = {v:2, mode, ts:Date.now(), ctx, metrics, findings, scores, final, confidence:conf, iterations:iter, threshold:App.settings.threshold, maxIter:App.settings.maxIter, log, provider:provLabel(), ...extra};
```

В промпте итогового шага (`pFinal`) модель получает вердикт как факт и не противоречит баллам. Это закрывает и вторую проблему со скриншота: итог начинался с «Вы уверенно держите продукт» при точности по продукту 1 из 10.

```
Итоговый балл: ${scores.total}/100. Вердикт (рассчитан по правилам, не меняй его): ${scores.verdict}.
Баллы по критериям: ${scores.rows.map(r=>r.name+' '+(r.score??'—')).join('; ')}
Не противоречь баллам: если «Точность по продукту» ниже 6, не хвали знание продукта; если ниже 6 «Структура» — не называй выступление структурным.
В verdict_label верни ровно этот вердикт.
```

**Как проверить.** 45 баллов → «Нужна повторная подготовка». 85 баллов без ошибок → «Готов к клиенту». 85 баллов и одна ошибка → «Нужна доработка». 70 баллов, обещание и две ошибки → «Нужна повторная подготовка».

## П4. Устаревшая база ЗП и штраф за «нет в базе»

**Что видно.** 10 утверждений из 30 получили статус «нет в базе», точность по продукту 1 из 10, уверенность проверки 72–80%.

**Причина.** Внутри приложения лежала первая база из «Пакета продавца». В ней нет условий из стандартной презентации 02.11.2026: СберПрайм за 399 ₽ в месяц, полная линейка вкладов, цифры по партнёрам, СберФест. Плюс каждое «нет в базе» снимало 0,5 балла: менеджер штрафовался за пробел в базе.

**Исправление.**
1. Встроенные базы заменены на проверенные версии: база ЗП v1.1 и база по выступлениям v2.1 (файлы `kb_zp_v1.1.md` и `kb_speech_v2.1.md` в комплекте; в `app.js` — константы `KB_ZP_DEFAULT` и `KB_SPEECH_DEFAULT`).
2. «Нет в базе» больше не снижает балл. Если таких утверждений четверть и больше, отчёт показывает предупреждение о пробеле в базе.

```js
function accuracyScore(claims){
  const list = Array.isArray(claims)?claims:[];
  const cnt = {}; for(const c of list) cnt[c.status]=(cnt[c.status]||0)+1;
  const notInKb = cnt['нет в базе']||0;
  const checkable = list.length - notInKb;      // «нет в базе» — пробел базы, а не ошибка выступающего
  const parts = FACT_STATUSES.filter(k=>cnt[k]).map(k=>k+': '+cnt[k]);
  const note = 'Утверждений: '+list.length+(parts.length?' ('+parts.join(', ')+')':'');
  const kbGap = list.length>=5 && notInKb/list.length>=0.25;
  if(!checkable) return {score:4, note: list.length ? note+'. Ни одно утверждение не удалось сверить с базой.' : 'В выступлении почти нет конкретики по продукту.', kbGap, notInKb};
  let s = 10;
  s -= 2.5*(cnt['ошибка']||0) + 3*(cnt['недопустимое обещание']||0) + 1*(cnt['неточно']||0);
  if(checkable<3) s = Math.min(s, 8);
  s = Math.max(1, Math.min(10, +s.toFixed(1)));
  return {score:s, note, kbGap, notInKb};
}
```

Предупреждение в отчёте (`renderReport`):

```js
    ${sc.kbGap?`<p class="banner">${sc.notInKb} утверждени${plural(sc.notInKb,'е','я','й')} не удалось сверить: в базе знаний ЗП нет этих условий. Это пробел базы, а не ошибка выступающего, и в балл не идёт. Дополните базу во вкладке «Базы знаний».</p>`:''}
```

**Важно про оценку со скриншота.** Даже после исправления точность останется 1 из 10: два недопустимых обещания, одна ошибка и четыре неточности снимают 12,5 балла. Это заслуженная оценка. Изменится то, что 10 утверждений «нет в базе» перестанут влиять на балл, а после обновления базы большая их часть станет проверяемой.

Объём промптов вырос: обе базы вместе — около 50 тыс. знаков. Для DeepSeek и GigaChat с контекстом от 32 тыс. токенов это нормально. В ручном режиме запрос для копирования теперь около 56 тыс. знаков.

## П5. Арифметика выступающего

**Что видно.** В цитате «800 рублей, 8400 рублей в год» сумма не сходится: 800 × 12 = 9 600, а 8 400 — это 700 × 12. Агент похвалил этот расчёт как доказательность.

**Исправление** (`app.js`, промпт `pFacts`, новый пункт 3; нумерация следующих пунктов сдвинута):

```
3) Проверь арифметику каждого расчёта, который приводит выступающий: «в месяц → в год» (×12), проценты от суммы, сложение выгод. Неверный расчёт — отдельная запись со статусом "ошибка": в kb — правильный результат, в fix — фраза с верным расчётом. Если ошибка может быть ошибкой распознавания, так и напиши в claim.
```

**Как проверить.** Синтетическая расшифровка с фразой «связь 630 рублей в месяц, это 8 тысяч в год» → запись со статусом «ошибка» и верным расчётом 7 560 ₽.

## П7. Персональные данные

**Исправление 1** — правило во всех промптах (`app.js`, константа `ROLE`):

```
- Не повторяй в ответе персональные данные из расшифровки: ФИО, имена с отчеством, должности конкретных людей, номера кабинетов, телефоны, суммы по счетам, названия компаний-клиентов. Заменяй их на [имя], [кабинет], [телефон], [компания] — и в цитатах тоже.
```

**Исправление 2** — маскирование до отправки в модель (`app.js`, перед `prepareInput`). Расшифровка у пользователя на экране не меняется; маскируется только текст, который уходит в модель, и цитаты в отчёте:

```js
/* Маскирование очевидных персональных данных перед отправкой в модель.
   Ловит телефоны, e-mail, длинные номера, имя+отчество, номера кабинетов.
   Имена без отчества не ловит — главная защита всё равно в выборе модели и правиле в промпте. */
function maskPII(t){
  return String(t)
    .replace(/[\w.+-]+@[\w-]+\.[\w.-]+/g, '[email]')
    .replace(/(?:\+7|(?<![\d])8)[\s(-]*\d{3}[\s)-]*\d{3}[\s-]*\d{2}[\s-]*\d{2}(?!\d)/g, '[телефон]')
    .replace(/(?<!\d)(?:\d[ -]?){15,18}\d(?!\d)/g, '[номер]')
    .replace(/(?:[А-ЯЁ][а-яё]+\s+)?[А-ЯЁ][а-яё]+(?:ович|евич|ьич|овна|евна|ична)(?![а-яё])/g, '[имя]')
    .replace(/(кабинет[а-яё]*|каб\.?)\s*№?\s*\d+[а-яё]?/gi, '$1 [№]');
}
function prepareInput(){
  const s = App.cur;
  const parsed = parseTranscript(s.transcript||'');
  parsed.lines = parsed.lines.map(l=>({...l, text:maskPII(l.text)}));
  parsed.text = parsed.lines.map(l=>l.text).join('\n');
```

**Как проверить.** «Заявление несите в кабинет 26, Катерина Викторовна, тел. +7 (921) 123-45-67, почта hr@firm.ru» → «Заявление несите в кабинет [№], [имя], тел. [телефон], почта [email]». Цифры условий («до 10%», «300 000 ₽», «185 000 бонусов») не затрагиваются.

# Приёмка

| Проверка | Ожидаемый результат |
|---|---|
| Запуск разбора без выбранной аудитории | Подсказка «Выберите аудиторию…», разбор не начинается |
| Расшифровка с таймкодами раз в 2 минуты | Ровный график темпа без нулевых минут |
| Расшифровка с репликами «Клиент: …» | Реплики не входят в число слов и темп выступающего |
| Итог ниже 50 | Вердикт «Нужна повторная подготовка» |
| Аудитория «Коллектив сотрудников клиента» | Нет красного блока «Выгоды для компании» |
| Много утверждений «нет в базе» | Предупреждение о пробеле в базе; балл за них не снижается |
| Ошибка в расчёте «в месяц → в год» | Отдельная запись со статусом «ошибка» |
| Имя с отчеством, кабинет, телефон в расшифровке | В отчёте [имя], [кабинет] [№], [телефон] |
| Телефон, ширина 390 px | Шапка в одну строку |
| Синтетический протокол `protokol-vystupleniya-ZP.txt` | Вердикт «Нужна доработка» или ниже; найдены ошибки: кешбэк 15%, СБП без ограничений, ипотека на 2 п.п., гарантированный выигрыш, СберПремьер от 150 тыс. |
| Эталон из документа 3, длительность 13:20, аудитория «Коллектив сотрудников клиента» | 90+ баллов, ни одной ошибки по продукту |

> Обратите внимание: синтетический протокол писался по базе из пакета продавца. Утверждение «переводы по СБП в любые банки без ограничений» по-прежнему ошибка (лимит 300 000 ₽ в месяц), но в ключе протокола указан старый лимит 100 000 ₽.

# Не вошло в v2.1 (бэклог)

- **«Вот» считается словом-паразитом всегда**, в том числе указательное («вот реквизиты»). На скриншоте «вот ×19» при норме паразитов 1 на 100 слов — завышения в балле нет, но в списке это смотрится странно. Вариант — показывать «вот» отдельно как «возможный паразит».
- **Длинные выступления.** Для записей дольше 25 минут стоит резать расшифровку на части по 10–15 минут и сверять каждую отдельно: на длинном тексте уверенность проверки падает.
- **Командный режим.** Сводка руководителю по всем менеджерам потребует хранения на сервере — только после закрытия Б1–Б3.
